# 烛龙 AI Agent 产品规格

本文定义晷迹的 **烛龙 AI**。烛龙 AI 是普通清单能力之外的可选辅助 Agent，用于复盘、分析习惯、拆解任务、生成 label 和提出排期建议。它不能成为 Day Todo、任务池、未完成池、已完成池或每日复盘的运行依赖。

## 设计原则

- 普通清单功能在没有网络、没有账号、没有 AI provider、AI provider 故障时必须完整可用。
- 烛龙 AI 只能生成建议草稿，不能直接改写历史日轨迹。
- 烛龙 AI 对当前日或未来计划的任何创建、排期、变更、延续、废弃、label 修改，都必须由用户确认或命中用户预先设置的托管授权后，再调用普通领域接口。
- 烛龙 AI 不依赖任何一本时间管理书或单一理论。它可以引用理论作为分析视角，但最终判断必须回到用户自己的任务轨迹证据。
- 烛龙 AI 的人格是独立、冷静、直指事实的复盘伙伴：它不讨好用户，不用道德化语言惩罚用户，也不把一次失败永久贴成人格标签。

## 命名与意象

烛龙 AI 的命名来自《苦昼短》中的“衔烛龙”意象：时间在日月寒暖中煎熬人寿，晷迹要做的不是美化时间，而是把用户真实留下的轨迹照亮。

《苦昼短》可作为烛龙页面、空状态、关于页或复盘入口的完整 slogan 元素。设计时不应把全诗做成压迫式大段正文，而应作为可展开、可滚动或仪式化的视觉元素。

> 飞光，飞光，劝尔一杯酒。
> 吾不识青天高、黄地厚，
> 唯见月寒日暖，来煎人寿。
> 食熊则肥，食蛙则瘦。
> 神君何在？太一安有？
> 天东有若木，下置衔烛龙。
> 吾将斩龙足、嚼龙肉，
> 使之朝不得回、夜不得伏。
> 自然老者不死、少者不哭。
> 何为服黄金、吞白玉？
> 谁似任公子，云中骑碧驴？
> 刘彻茂陵多滞骨，嬴政梓棺费鲍鱼。

诗文本采用维基文库《苦昼短》通行文本：https://zh.wikisource.org/zh-hans/苦昼短 。后续如果要做古籍校勘版本，可另建文案资产，不影响产品规则。

## Provider 模型

烛龙 AI 必须支持自定义 provider。

核心字段：

- `providerId`
- `displayName`
- `kind`：OpenAI-compatible、本地模型、自定义 HTTP
- `baseURL`
- `model`
- `apiKeyRef`
- `extraHeaders`
- `enabled`
- `createdAt`
- `updatedAt`

规则：

- API Key 只能进入系统 Keychain 或等价安全存储，不能进入普通配置文件、日志、导出数据包或崩溃报告。
- provider 未配置或不可用时，烛龙入口显示为可配置状态，普通清单功能不降级。
- provider 配置允许测试连接，但测试连接失败不能阻止用户继续使用清单。
- 第一版不做内置云端账号绑定。未来可以增加原生云 AI provider，但不能移除自定义 provider。

## 数据访问边界

烛龙 AI 默认只读取用户主动选择的范围。

可选范围：

- 当前 Day Todo
- 某个历史日
- 最近 7 天、30 天或自定义日期范围
- 未完成池
- 已完成池
- 任务池
- 用户选中的任务链
- label 和任务分类统计

规则：

- 每次向远程 provider 发送数据前，界面必须让用户知道将使用哪些范围的数据。
- 不能发送数据库文件、内部 ID、Keychain 值或同步端点配置。
- 对外发送的任务数据应尽量使用最小必要字段：标题、日期、状态、子任务、延续次数、复盘文本、label。
- 烛龙生成的分析结论必须带可追溯证据，例如“过去 14 天 6 个大任务中有 5 个发生延续复制”。

## 托管授权与全权管家

烛龙 AI 需要预留从“建议草稿”升级到“全权管家”的路径。全权管家不是让模型绕过晷迹规则，而是让用户预先授权烛龙在限定范围内自动应用合法建议。

权限档位：

- 建议模式：烛龙只输出建议草稿，不执行。
- 逐条确认模式：烛龙生成一组建议，用户逐条确认后执行。
- 全权管家模式：烛龙在用户指定的数据范围、操作类型、次数上限和有效期内自动执行，执行后必须给出记录供用户复核。

全权管家的典型适用动作：

- 给任务池任务补充建议 label。
- 把用户已经授权的任务池任务排到未来 Day Todo。
- 为大任务添加子任务草稿。
- 根据用户设定的规则，把历史未完成任务延续到某个未来日期。
- 生成每日复盘草稿或复盘问题。

全权管家的硬约束：

- 不能删除历史日轨迹。
- 不能覆盖式编辑已有日轨迹的任务定义。
- 不能无痕移动历史任务，只能延续复制、废弃或走变更方案。
- 不能在用户未授权的数据范围外读取和发送任务数据。
- 不能绕过普通领域接口直接写数据库。
- 每次托管执行必须留下执行记录，记录来源建议、执行动作、执行结果和失败原因。

## 核心能力

### 每日复盘助手

输入：

- 当日 Day Todo
- 当日复盘草稿
- 当日完成、未完成、已延续、已变更、已废弃统计
- 相关任务链历史

输出：

- 今日事实摘要
- 未完成原因假设
- 明日风险提示
- 可行动建议
- 可选复盘文本草稿

约束：

- 不能改写每日复盘统计事实。
- 不能替用户自动提交复盘文本。
- 输出要区分事实、推断和建议。

### 习惯画像

烛龙可以根据历史轨迹提出阶段性画像，但只能作为可修正假设。

候选画像包括：

- 好大喜功型：经常创建大任务，子任务拆解不足，延续次数高。
- 拖延型：任务多次延续，完成集中在压力边界附近。
- 估时偏差型：每日任务量持续超过历史完成能力。
- 完美主义卡住型：任务变更多、完成少，大任务长期不收敛。
- 被动响应型：当日新增和回池频繁，原计划被外部事务打断。
- 碎片化切换型：大量小任务开始，但完成轨迹分散。
- 稳定推进型：大任务能拆解成子任务，并在多日内持续收敛。

约束：

- 画像必须带证据和置信度。
- 画像不能永久写入用户身份，只能作为某个时间窗口的分析结果。
- 画像文本不能羞辱用户，不能给医疗或心理诊断结论。

### 大任务拆解

烛龙可以帮助用户把一个大任务拆成子任务。

输入：

- 任务标题、描述、已有子任务
- 用户目标日期或可投入时间
- 历史同类任务完成情况

输出：

- 建议子任务列表
- 推荐执行顺序
- 风险点
- 需要用户补充的问题

约束：

- 建议子任务默认是草稿。
- 用户确认后才能创建子任务。
- 已经产生日轨迹的任务仍不能覆盖式编辑标题和描述；需要改变任务边界时仍走子任务或变更方案。

### 自动排期

烛龙可以提出排期建议。

输出类型：

- 从任务池安排到某个 Day Todo
- 从未完成池延续到目标日期
- 把大任务拆成多天推进计划
- 提醒某天任务量超过历史完成能力

约束：

- 烛龙不能无确认创建日轨迹。
- 对历史未完成任务，烛龙只能建议延续复制或废弃，不能建议无痕改期。
- 对未来计划，烛龙可以建议未来日期之间的调整，但用户确认前不落库。

### Label 分类

烛龙支持两种 label 模式。

用户预设 label：

- 用户先创建固定 label。
- 烛龙把任务建议分类到这些 label。
- 用户确认后写入任务 label。

自动生成 label：

- 用户不预设 label。
- 烛龙根据历史任务、完成轨迹和复盘文本生成若干组 label 候选。
- 用户选择一组后，烛龙再对任务做分类建议。

规则：

- label 是组织和分析维度，不是任务状态。
- label 修改不允许改写历史日轨迹事实。
- label 自动分类必须可批量预览、逐条撤回、逐条确认。

### 理论参照分析

烛龙不绑定 GTD、四象限、番茄、PARA、Zettelkasten 或其他任何单一理论。

它可以回答：

- 按某个理论看，我现在的问题是什么？
- 这个理论适不适合我？
- 如果不用这个理论，仅从我的轨迹看，我应该怎么调整？

约束：

- 理论只能作为镜头，不是产品默认真理。
- 推荐必须回到用户自己的日轨迹、延续次数、完成率、子任务收敛情况和复盘文本。

## 可补充能力

- 延续风险预警：某任务达到第 N 次延续时提示用户重新拆解或废弃。
- 承诺预算：根据过去完成能力提示今天是否承诺过量。
- 任务边界审计：发现标题过大或含糊时建议拆子任务。
- 复盘追问：根据当日结果生成 1 到 3 个复盘问题。
- 周期性模式发现：识别某些 label、日期或时间段更容易延期。
- 任务命名助手：把含糊任务改写成可执行版本，但已有日轨迹任务仍必须走变更方案。
- 冲突检查：发现同一天多个大任务都需要高认知投入时提示冲突。
- 废弃建议：对长期不收敛且不再符合目标的任务链建议废弃。
- 导出 AI 分析报告：生成 Markdown 报告，但不替代真实复盘数据。

## UI 入口

建议第一版提供：

- 左侧导航中的“烛龙 AI”入口。
- Day Todo 右侧复盘区中的“让烛龙分析今日”按钮。
- 任务详情中的“拆解子任务”和“排期建议”按钮。
- 未完成池中的“分析延续原因”按钮。
- 设置中的 provider 管理入口。

如果 provider 未配置：

- 烛龙 AI 页面显示配置引导和《苦昼短》意象。
- Day Todo、任务池、未来计划、未完成池、已完成池仍完全可用。

## 风险评估

- 隐私风险：用户任务和复盘文本可能包含敏感信息。必须最小化发送范围，并让用户显式确认。
- 错误建议风险：AI 可能误判任务意图或低估工作量。所有写入动作必须预览和确认。
- 产品心智风险：AI 可能喧宾夺主，让晷迹变成聊天工具。入口应克制，核心清单仍是第一层体验。
- 标签污名风险：习惯画像可能让用户感到被贴标签。画像必须是时间窗口假设，并带证据和置信度。
- Provider 锁定风险：如果只支持一家模型，会违背用户自定义 provider 的要求。provider 层必须抽象。

## 回滚方案

- 使用 feature flag 关闭烛龙 AI 入口。
- 保留 provider 配置但停止发起请求。
- 已经由用户确认创建的任务、label、复盘文本是普通领域数据，不随 AI 入口关闭而删除。
- AI 建议草稿可以整批清理，因为它不是历史事实。

## 灰度方案

1. 只开放 provider 配置和手动测试连接。
2. 开放只读复盘分析，不允许生成写入建议。
3. 开放子任务拆解草稿，用户逐条确认。
4. 开放 label 自动分类草稿，用户批量预览后确认。
5. 开放排期建议草稿，仍禁止无确认写入。

## 监控指标

本地优先前提下，第一版优先记录本机诊断指标，不上传个人数据。

- provider 请求成功率、失败原因、延迟区间
- AI 建议生成次数
- 建议被采纳、修改、拒绝的比例
- AI 生成后被撤销的普通操作比例
- 用户关闭 AI 入口或清空 provider 的次数
- 隐私确认弹窗取消率
