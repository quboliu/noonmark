# 删除分组只解除当前关系，不改写历史

**Status**: Accepted  
**Date**: 2026-07-26  
**Risk**: A 级——跨任务批量关系变更、当天快照、同步审计与用户确认

## Context

既有分类 Module 提供“归档”和“硬删除”。归档只停止新关联，既有任务仍保留当前分组；硬删除只允许从未被使用的分类项。两者都不能表达用户需要的产品语义：删除一个正在使用的分组，同时保留过去任务当时所属分组的真实记录。

当前分组关系属于任务链，历史页面则读取日轨迹上的独立分类快照。删除操作若直接移除分类身份，会形成悬空历史引用；若只隐藏目录项，今天和未来任务仍会继续携带该分组。

## Decision

新增“分组删除”领域操作，并把它作为一个候选 Engine 上的原子事务：

1. 找出所有当前关系仍指向目标分组的任务链，逐条解除主分类关系，标签保持原样。
2. 今天已经产生历史分类快照的相关轨迹追加一条主分类为空的新事件；旧事件仍保留。今天之前的快照完全不修改。
3. 目标分组进入归档生命周期，不再接受新关联；分类身份、名称版本、关系历史和历史快照继续存在。
4. 任一步失败时不发布候选 Engine，不允许出现部分任务已去分组、分类仍活动或当天快照未对齐的状态。
5. UI 使用显式破坏性确认，说明“今天及未来转为未分组、历史保留”。普通归档继续保留，用于“停止新使用但保留当前归属”的不同意图。

分组删除复用既有 `setCurrent`、快照事件和 lifecycle commit，因此 SQLite、数据包与同步 wire 不增加第二套事实；离线设备按既有因果提交重放关系解除与归档。

## Consequences

- 任务池、Day Todo 与未来计划立即显示为未分组；历史页面仍显示当时分组。
- 当天已形成快照的任务以追加事件反映最新去分组状态，同时保留当天较早事件用于审计。
- 恢复归档分组只让该分组重新可选，不会自动恢复已经解除的任务关系。
- 从未使用的分组仍可走既有硬删除；有任何历史引用的分组不能硬删除。

## Verification

- Core 测试覆盖过去、今天、未来与任务池四类任务，并验证标签不变、当天事件追加、过去快照不变。
- 失败注入以倒退 mutation time 证明整个删除操作保持原子。
- 真实 App E2E 覆盖分组管理入口、破坏性确认、当前关系解除与重启持久化。
