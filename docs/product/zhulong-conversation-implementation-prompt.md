# 烛龙 Codex 式对话页面像素级实现约束

- 日期：2026-07-21
- 参考：用户提供的 Codex App 对话页截图（仅作交互与视觉语言参考，不作为晷迹视觉回归基线）
- 适用：`ZhulongSessionStreamPage` 的四个投影，以及其共享的常驻 composer。

## 实现提示词

在 macOS 明亮模式中实现一个以连续对话为主角的烛龙页面。它应当让人感觉在和一个可靠、能持续理解上下文的助手交谈，而不是在操作流程 dashboard、审批表单或事件日志。烛龙保留单题会话、授权、规划与 Todo 确认的领域约束，但这些约束不能主导默认视觉层级。

页面在主工作区内使用白色／暖白连续画布；会话正文与 composer 共享不超过 840pt 的可读轴，在可用空间中居中。正文顶部留 28pt，消息之间留 28–36pt 的呼吸间距；长回答靠段落、标题、列表与代码块自然展开，不用外层卡片、描边或彩色背景。正常烛龙消息没有头像、名称、时间戳、sparkles 图标、状态 pill 或纵向强调条；使用可选择的 Markdown 正文，主文本约 15–16pt、行高约 1.55。标题、列表、引用和代码沿用 Markdown 的语义层级，而不是被缩成系统日志。

用户消息右对齐，最大宽度为可读轴的约 68%，使用非常浅的中性灰填充、18–20pt 连续圆角、水平 16pt／垂直 11pt 内边距；文字约 14–15pt，黑色或近黑色。用户气泡之外不显示“用户”、时间、头像或其他元数据。系统事实（授权已记录、Provider 正在响应、运行失败）不是第三种聊天角色：只在确有意义时显示为弱化的单行文字，置于对应消息附近，不挤占阅读节奏。

普通对话使用真实 SSE 文本流，不得以延时逐字动画冒充。首个片段到达后，正文底部显示无卡片的临时烛龙 Markdown 消息和细光标；每个后续片段立即合并到该消息。Provider 正常完成且完整内容通过既有校验后，才原子替换为正式烛龙消息；用户主动停止时，取消当前运行并把已经落屏的可见正文保存为 stopped 回复。规划、Todo、复盘与任务池分析的结构化输出仍等待完整 JSON 后校验，不能把半截 JSON 当成产物。若 Provider 在任何片段前拒绝 SSE，可回退到既有完整响应；一旦已显示片段则不得重发请求，避免重复回答。

页面顶端仍保留晷迹需要的 56pt 薄标题栏：中央只显示“烛龙”，左侧为全部会话，右侧为唯一的“视图 · 当前投影”入口和必要的详情栏展开动作；不得在 composer 或流中复制该菜单。可用宽度低于 720pt 时，左右文字控制收成 32×32pt 图标，标题始终以主内容区为轴居中且不与控制重叠。暂停／继续收进视图菜单。标题栏不是仪表盘，不能显示诗句、会话副标题、意图 badge、流程状态 badge 或第二层导航。

composer 固定停靠在页面底部，但像一块独立的轻质输入面板，而不是一条窄表单：最大宽度与正文一致，最小高 84pt，20pt 圆角，白色表面、1pt 柔和边界和极轻的下方阴影。文本输入区位于上半部，左上留 16pt；下方只保留右下 30×30pt 圆形主动作，不显示键盘提示或重复的数据范围小字。空闲时为发送，Provider 运行时同一按钮替换为停止；不伪造附件、语音或模型选择能力。Enter 发送，Shift+Enter 换行，按钮与键盘动作调用同一个发送路径。Composer 在四个投影中位置、外观与交互完全相同。

权限、Provider 切换／过期、Todo 写入和复盘保存仍需用户确认，但只有在用户必须做决定时才作为一条烛龙式内联动作出现。不要在普通聊天开始时自动展开计划表、Todo diff、审批卡或多段表单，也不要要求用户从消息右键菜单切换到另一套流程。

当自然对话已经形成可执行方案时，Provider 在自然语言正文后附带严格的结构化对话产物。协议数据不能显示在聊天中；完整响应通过校验后，任务方案直接投影为内联任务草稿卡，保留一个或多个父任务、各自子任务、描述、附言及任务池／今天／未来日期落点。用户可以直接编辑和增删，也可以继续对话要求烛龙返回完整修订版本。点击“提交任务”或发送明确的“提交”消息必须调用同一条原子写入路径；讨论“如何提交”、否定提交或仍在修改的消息不能被识别为授权。每日复盘采用相同的“结构化产物—内联编辑—一次提交”原则。

任务草稿是当前确有独立信息与操作的单一轻面板；父任务和子任务依靠对齐、留白与分隔线建立层级，不为每一层重复添加卡片、彩色图标、徽章和尾箭头。正常 Provider run、草稿发布、授权记录和应用成功事件属于内部账本，不得作为流程进度插入聊天正文；只有错误、失效或当前必须处理的授权边界可以打断对话。

四个投影只改变信息的组织方式，不能改变对话的首要性：

1. `conversation` 是纯净时间序列，完全遵守上述聊天布局。
2. `dossier` 可以以极淡的时间／事实分隔辅助回顾，但没有卡片边框或时间线装饰。
3. `chapters` 可以在相关消息前显示低强调章节文字，不能把消息塞入手风琴卡片。
4. `weave` 可以保留左右角色关系，但不得使用双轨节点、因果线或 dashboard 卡片；用户仍为右侧气泡，烛龙仍为左侧 Markdown 正文。

整页以字号、行距、对齐、留白和文本语义建立秩序。每新增一个视觉单位都必须承载用户当前可执行的独立操作；否则删除它。不要复制 Codex 的品牌、名称或无实际能力的控件，只复现其对话优先、克制、稳定且可长读的体验原则。

## 验证约束

- 真实 `.app` E2E 必须截图四个投影，并通过原生可访问性节点确认只有右上角存在视图菜单、composer 固定存在、输入入口可聚焦。
- 真实交互必须覆盖 Enter 发送、Shift+Enter 换行、首条 Provider 片段在正式回复落盘前出现在真实视图树、通过真实停止按钮取消运行并保留部分正文、重启回读 stopped 记录、Provider 身份改变后保留输入、重新授权并继续对话。
- 当前快速迭代每一轮的结构化产物真实 `.app` E2E 至少覆盖父任务与子任务形态、任务池／今天／未来日期落点、真实按钮提交、原子写入回执及持久化引擎可见性；截图不得显示协议 JSON 或正常内部账本进度。
- 功能点敲定后的最终门禁再完整覆盖物理内联编辑、明确文字提交、重启后目标页面可见性与四种对话投影，避免在快速体验阶段把完整门禁误当成每轮启动前置条件。
- API Key 在 Settings 内保存后仅显示掩码，不能把 Keychain 术语或明文暴露到界面、日志或截图。
