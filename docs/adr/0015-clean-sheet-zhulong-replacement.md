# 烛龙采用 clean-sheet 整体重写与一次性 cutover

当前烛龙产品、应用编排和 UI 不作为新系统的设计或实现参考；新的会话、记忆、权限、事件历史、规划草稿、承诺风险、Provider 编排和会话工作空间按已确认领域模型 clean-sheet 重写。新系统完成并通过真实用户路径验证后，一次性替换旧烛龙并删除旧实现，不提供用户可见的 V1／V2 双入口或长期 fallback。

**Consequences**

- 旧工作区卡片、能力按钮、草稿收件箱、context rail 和 App 内固定模板生成逻辑全部废弃。
- 新实现不以旧 `SuntraceStore` 烛龙状态或既有 AI UI 接口为兼容目标。
- `SuntraceCore` 的任务链、日轨迹、历史不可改写规则和用户 Todo 数据继续保留；可安全迁移的 Provider 凭证不得丢失。
- 旧代码可以在开发期间暂时存在，但不能作为新产品路径、设计基线或运行 fallback；cutover 与旧代码删除在新路径完整验证后同批完成。
- cutover 前必须覆盖真实 `.app` 每日收尾路径、持久化、sidecar 加密、权限与事件审计、Provider live smoke、视觉回归和 DMG 安装启动。

## 风险与回滚

- 最大风险是新路径未达到每日收尾、任务成形、权限、审计或 Todo 应用能力对等便提前切换。cutover gate 必须逐项持有真实运行证据，不能以 build 或 mock 单测代替。
- cutover 前可以关闭开发中的新入口；cutover 后若出现高风险缺陷，只关闭烛龙旁路并保留加密 sidecar 与 Provider 凭证，普通 Todo 保持可用。不得重新启用旧固定模板作为运行 fallback。
- 新路径只通过普通领域接口应用 Todo；关闭烛龙不删除已经由用户确认形成的核心任务事实。

## 灰度与监控

1. 独立模块先覆盖会话、授权、Provider 发送、加密和恢复。
2. 内部 App 路径依次开放只读会话、草稿生成、Todo diff 预览和用户确认应用。
3. 能力对等审计与全部真实产物验证通过后，一次性切换并同批删除旧实现。
4. 本机诊断只记录状态、失败类别、延迟区间和恢复结果；不上传或打印会话正文、任务内容、Provider 响应和凭证。
