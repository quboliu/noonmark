# 烛龙“过度承诺”判断的证据基础

调研日期：2026-07-10  
调研问题：在个人 Todo / 日计划产品中，怎样用科学、真实、可解释且可本地计算的依据判断“过度承诺”，避免只按任务条数或模型感觉？

## 结论

烛龙不应把“过度承诺”实现为一个由 LLM 主观打出的标签，也不应使用“明天超过六项任务”之类的通用常数。第一版最可靠的定义是：

> 在用户选择的兑现风险水平下，当前承诺的工作量高于该用户在可比历史日中实际兑现过的工作量；现有证据显示完整兑现的概率偏低。

这一定义必须同时满足以下条件：

1. 当前计划与历史样本使用同一种、可比较的工作量单位。
2. 历史样本来自预先定义的可比日，而不是事后挑选有利样本。
3. 输出概率范围、样本数和不确定性，而不是只输出一个确定标签。
4. 把烛龙的预测和次日真实结果落盘，持续检查预测是否校准。
5. 用户拥有最终取舍权；风险阈值表达用户对“计划必须全部兑现”的要求，不是系统代替用户决定多少风险可接受。

当前晷迹已经有很好的任务轨迹基础，但没有任务实际耗时，也没有独立的任务工作量估计。因而在现有数据条件下，烛龙最多能给出“任务条数或历史兑现轨迹异常”的弱提示，不能把它表述为已证实的真实容量超载。要形成强提醒，需要新增与 `子任务难度权重` 分离的工作量数据和明确的日承诺快照。

## 一手证据

### 规划谬误要求使用“外部视角”

Buehler、Griffin 与 Ross 对多个学术和非学术任务的实验发现，参与者预测自己的完成时间时会过度乐观，并主要关注当前计划情境，忽略过去类似任务的分布信息；提示参与者把相关历史经验与当前预测连接起来，能消除平均方向上的乐观偏差。不过，该操作并没有降低绝对预测误差，论文也明确指出：只有历史记忆可靠且当前任务与历史项目可比时，历史经验才有预测价值。这意味着产品不能只做“提醒你过去也延期过”，而要使用系统记录的、可比的历史数据，并保留不确定性。[Buehler、Griffin 与 Ross（1994）原始论文](https://bear.warrington.ufl.edu/brenner/mar7588/Papers/buehler-et-al-1994.pdf)

Kahneman 与 Lovallo 将过度乐观预测归因于“内部视角”：规划者把当前问题当成独特事件，围绕当前方案和情境推演，却忽略过去结果的统计分布。对烛龙的直接启示是，模型生成的任务拆解只能补充当前计划的内部视角，不能代替基于历史轨迹的基准率。[Kahneman 与 Lovallo（1993）原始论文](https://doi.org/10.1287/mnsc.39.1.17)

英国 Homes England 的第一方 Reference Class Forecasting（RCF）指南把外部视角操作化为三步：选取过去的相似项目、建立结果的概率分布、再根据当前项目相对参考类的风险作调整。指南同时要求参考类“尽可能广，但又必须足够相似”，避免为了匹配而丢失有价值的数据，也避免把不相似的样本混在一起。该指南面向大型项目，不是个人 Todo 的直接验证，但这三步适合作为烛龙本地证据引擎的设计原则。[Homes England RCF 指南](https://www.gov.uk/government/publications/optimism-bias-and-contingency-at-homes-england/optimism-bias-and-contingency-at-homes-england-accessible-version)

英国财政部 2026 年 Green Book 进一步要求，乐观偏差调整应优先来自本组织过去相似项目中“预测值与实际结果”的误差，而不是只套通用加成。迁移到晷迹的工程含义是：优先使用同一用户的历史预测误差和兑现结果，群体平均值只能作为尚无个人数据时的明确外部先验，不能冒充个人事实。[HM Treasury Green Book（2026）](https://www.gov.uk/government/publications/the-green-book-appraisal-and-evaluation-in-central-government/the-green-book-2026)

### 任务条数与“简／中／难”不能等同真实工作量

NASA-TLX 的原始研究与 NASA 当前官方说明把工作负荷分成心理需求、身体需求、时间需求、表现、努力和挫折六个维度；其要点不是让 Todo 产品直接采用 NASA-TLX，而是说明“难度”不是一个可自然等同于时长或总负荷的单一量。[Hart 与 Staveland（1988）原始研究](https://doi.org/10.1016/S0166-4115(08)62386-9)、[NASA-TLX 官方说明](https://www.nasa.gov/human-systems-integration-division/nasa-task-load-index-tlx/)

因此，两项任务和八项任务谁更重，单凭条数无法判断；一个“难”子任务也没有证据等于三个“简”子任务的工时。晷迹现有领域模型也已经明确把 `子任务难度权重` 定义为进度计算权重，并明确 `_Avoid_: 工时估算`，所以绝不能悄悄复用它来计算容量。[CONTEXT.md](../../CONTEXT.md)、[SuntraceCore Models](../../Sources/SuntraceCore/Models.swift)

可比较工作量必须另建字段。可选方案包括用户预估的专注分钟、个人工作量点数或粗粒度大小档位，但其数值只能在同一用户、同一度量制度内比较。若要声称“时间容量”，还必须记录实际主动投入时长；仅有创建时间和完成时间不能推导实际工时，因为二者之间可能包含等待、睡眠、其他工作和跨日排期。

### 风险必须以概率和区间表达

RCF 的第一方实践不是只给单点答案，而是展示不同 P-level 对应的结果范围，让决策者根据风险偏好选择；同一指南也指出，没有一个适用于所有场景的唯一 P-level。[Homes England RCF 指南](https://www.gov.uk/government/publications/optimism-bias-and-contingency-at-homes-england/optimism-bias-and-contingency-at-homes-england-accessible-version)

当烛龙把“可比历史日是否完整兑现当前等级的承诺”当成二元事件时，可以用 Wilson score interval 显示该成功率的区间，而不是只显示 `k / n`。Wilson 的方法来自对二项比例推断的原始研究，尤其适合提醒产品团队：小样本下的 `2/3 = 67%` 并不代表有 67% 的确定性。[Wilson（1927）原始论文](https://doi.org/10.1080/01621459.1927.10502953)

但 Wilson 区间的覆盖性质依赖二项样本的稳定性和近似独立性。个人每日状态会随工作安排、健康和生活阶段改变，因此它在烛龙中只能是透明的统计近似，不能包装成严格的人体能力证明。

### 滚动窗口没有通用的“科学天数”

短窗口能更快反映最近变化，却更容易受偶然波动影响；长窗口样本较稳定，却可能混入已经过时的生活阶段。Bifet 与 Gavaldà 针对变化数据流的原始研究正是从这个固定窗口取舍出发，提出按检测到的分布变化自动扩大或缩小窗口的 ADWIN 方法。[Bifet 与 Gavaldà（2007）原始论文](https://www.cs.upc.edu/~gavalda/papers/adwin06.pdf)

这不意味着第一版 Todo 产品应直接使用 ADWIN：个人可比日数据稀疏，且不一定满足论文的流数据假设。可以确定的是，没有一手证据支持把固定 7、14、30 或 90 天宣称为普适答案。第一版更诚实的做法是并列展示“近期参考类”和“较长期参考类”；二者冲突时输出“基线可能已变化，证据不稳定”，而不是选择对当前结论最有利的窗口。

### 预测必须接受后验校准

Gneiting 与 Raftery 指出，概率预测的目标是在保持校准的前提下提高分布的精确度；严格 proper scoring rule 会鼓励如实报告概率，也能用于比较预测方法。二元事件可使用 quadratic / Brier score 评估预测概率与实际结果的差距。[Gneiting 与 Raftery（2007）原始论文](https://sites.stat.washington.edu/people/raftery/Research/PDF/Gneiting2007jasa.pdf)

因此，烛龙每次说“明日完整兑现概率约为 40%”时，必须保存当时的概率、参考类、样本数、数据窗口、模型版本和用户最终采用的计划；次日再记录是否兑现。只有经过一段前瞻验证后，产品才能知道 40% 的日子是否真的约有四成兑现。没有这条反馈回路，“科学评分”仍只是未经校验的公式。

## 当前仓库能证明什么

以下结论来自当前源码和领域定义，不以既有文档中的产品愿望代替运行数据。核心字段位于 [SuntraceCore Models](../../Sources/SuntraceCore/Models.swift)，现有本地证据计算位于 [LocalInsightAnalyzer](../../Sources/SuntraceAI/LocalInsightAnalyzer.swift)。

| 现有信号 | 可以支持的结论 | 不能支持的结论 |
| --- | --- | --- |
| `DayTrace.date` 与锁定 Day Todo | 某项承诺在哪个自然日留下轨迹 | 用户当天实际有多少可工作时间 |
| `completed / unfinished / continued / returnedToPool / abandoned` | 原日承诺最后怎样结算；可计算历史兑现与未兑现分解 | 未完成的心理原因；“任务过多导致失败”的因果关系 |
| `changed` 与变更链路 | 用户重定义了任务边界 | 旧承诺算成功还是失败；必须根据产品定义和替代任务结果另行处理 |
| `continuationSeq` | 同一任务链跨日延续的次数 | 每次延续投入了多少时间；延续是否由过度承诺造成 |
| `manualProgressPercent`、子任务状态 | 用户记录的部分进展 | 实际工时或剩余工时 |
| `SubtaskDifficulty = 1/2/3` | 子任务加权进度 | 1/2/3 小时、线性努力或跨任务可比负荷 |
| `createdAt / completedAt / settledAt` | 记录创建、完成和日结束结算的时点 | 两时点之间的主动工作时间 |
| `DailyReviewStats` | 某日各状态的项目数 | 这些项目工作量相等；用户已经过载 |
| 用户已确认的复盘原因 | 对该日的用户归因 | 未经确认推广成长期人格或普遍因果规律 |

现有 `LocalInsightAnalyzer` 的 `completion_rate` 把已完成、未完成、延续和废弃日轨迹放入同一个分母，适合做授权范围内的描述性事实；它没有参考类、工作量单位、时间窗口比较或置信区间，因此不能单独作为“过度承诺”判定器。

还有一个关键数据缺口：当前 `DayTrace.createdAt` 能说明任务何时进入某日，却没有“用户在何时确认这是该日承诺集合”的独立快照。日内临时新增任务和前一晚确认的计划会混在同一 Day Todo 中。若不新增承诺快照，系统只能分析“该日最终出现的任务集合”，不能准确评估“用户开始这一天时是否承诺过量”。

## 推荐的本地判定模型

### 1. 先定义预测目标

不预测抽象的“用户能力”，而预测一个可在次日验证的事件：

> 在所选日期结束前，用户是否兑现了本次明确确认的承诺集合。

产品必须先决定“兑现”的领域语义。建议：

- `completed` 计入兑现工作量。
- `unfinished`、`continued`、`returnedToPool`、`abandoned` 表示原日期承诺没有按原样兑现，但 UI 必须展示具体分解，不能统一称为失败。
- `changed` 不直接计成功或失败；跟踪替代任务后按显式规则结算，或标为无法判断。
- 日内新增但不属于该承诺快照的任务，记录为额外完成量，不反过来污染晨间计划的兑现率。
- 有子任务的任务可以另外显示部分推进，但部分推进不应被偷偷等同于完整兑现。

### 2. 建立独立的工作量单位

强判定至少需要以下新数据：

- `commitmentSnapshot`：用户确认的日期、任务集合、当时版本和确认时间。
- `estimatedWorkload`：任务级工作量，独立于优先级和子任务难度。
- `availableCapacityContext`：该日用户声明的可用时间档位，至少能区分正常日、短日和异常日。
- 可选 `actualEffort`：若产品提供专注计时或完成时快速补录，才能校准时间估计误差。

如果采用个人工作量点数，烛龙能预测的是“按用户自己的估算制度，多少点通常能兑现”；如果采用分钟但没有实际时长，仍只能预测“估算分钟的兑现”，不能声称测得真实工时。

### 3. 预先定义参考类

参考类选择规则必须在看结果之前确定，并在 AI 决策说明中披露。第一版可以从以下特征开始：

- 同一用户。
- 相同的工作日／周末类型。
- 相同的可用容量档位。
- 相同的工作量度量版本。
- 若样本充足，再按用户确认的任务类型或 Label 分层。

规则需要在“足够相似”和“样本足够多”之间取舍。不能因为某次结论不合预期而临时增加或删除筛选条件。没有相似样本时，正确输出是“没有可靠参考类”，而不是让 LLM 用常识补数字。

### 4. 计算可解释的兑现概率

设当前承诺工作量为 `L`。从参考类中只选择对 `L` 有信息量的历史日，例如这些日子的已确认计划负荷与 `L` 在同一预设区间；不要把只计划了少量工作的日子当成“无法完成 L”的证据。

对每个可比历史日定义：

- `y = 1`：该日完整兑现了确认的承诺集合。
- `y = 0`：该日没有完整兑现。

令 `n` 为可比日数量，`k = Σy`，报告：

- 历史兑现率 `p̂ = k / n`。
- Wilson 95% 区间 `[lower, upper]`。
- 候选计划负荷 `L`、参考类规则、日期范围和各结算结果分解。
- 近期窗口与长期窗口的结果是否一致。

用户选择最低可接受兑现概率 `τ`。这个值是风险偏好，不是科学常数。判定状态建议为：

- `风险证据较强`：`upper < τ`，即使考虑当前统计不确定性，兑现概率仍低于用户要求。
- `证据支持可承诺`：`lower ≥ τ`。
- `证据不确定`：区间跨过 `τ`、近期与长期窗口冲突、参考类不稳定，或工作量不可比。
- `无资格判定`：没有有效参考类、没有承诺快照或没有一致工作量单位。

这一规则刻意使用区间上界作为强提醒门槛，降低小样本误报。它仍然只是产品内的统计决策规则，不是关于个人极限的科学诊断。

另一种可解释视图是展示历史完成工作量分布：`P(历史完成量 ≥ L)`。但历史日若原本只安排了小于 `L` 的工作，就没有机会证明可以完成 `L`，属于受计划上限影响的截尾观察，不能简单计为失败。第一版优先使用相近计划负荷下的“整日是否兑现”，比把所有历史完成量混成一个容量分布更稳妥。

### 5. 处理最低样本和窗口变化

不存在已在个人 Todo 场景验证过的统一最低样本数。Homes England 的 RCF 指南提到 20–30 个可比项目可开始建模，但这是大型项目实务经验，不能直接变成“烛龙必须有 20 天”的科学定律。[Homes England RCF 指南](https://www.gov.uk/government/publications/optimism-bias-and-contingency-at-homes-england/optimism-bias-and-contingency-at-homes-england-accessible-version)

推荐使用结果驱动的样本政策：

- 样本数始终显式显示。
- 不用 `n ≥ 某常数` 自动制造确定性；让 Wilson 区间宽度和参考类稳定性决定能否强提醒。
- 样本很少时只展示描述性历史，不输出强判定。
- 近期和长期结果冲突时，输出“可能发生基线变化”，请用户确认工作或生活条件是否改变。
- 用户确认发生长期变化后，旧数据仍保留用于审计，但不默认进入当前参考类。
- 若未来样本规模足够，可评估 ADWIN 或其他变化检测；在此之前，不以复杂算法掩盖稀疏数据。

### 6. 保存预测并校准

每次建议应落盘：

- 预测事件定义。
- 预测概率和区间。
- 用户选择的 `τ`。
- 参考类过滤规则、样本日期与 `n/k`。
- 近期／长期窗口结果。
- 工作量单位与版本。
- 最终被用户确认的计划。
- 算法／模型版本。

日结束后记录真实事件 `y`。本地周期性计算 Brier score `mean((p - y)²)`，并以概率分箱检查可靠性，例如预测在 60% 左右的日子实际是否约六成兑现。若持续过度自信，应扩大区间或下调预测；若参考类规则改变，必须保留版本，不能把新旧预测混为同一模型表现。

LLM 可以把这些证据解释成自然语言、提出减少或替换任务的方案，但不得生成概率、修改样本或覆盖统计引擎的“不确定”状态。

## 建议的 UI 决策说明

强提醒至少显示：

- “你准备承诺多少工作量”。
- “比较了哪一类历史日”。
- “共有多少个可比日，完整兑现了多少次”。
- “估计概率区间是多少”。
- “近期与长期是否一致”。
- “当前缺少哪些信息”。
- “减少哪些承诺后会落到什么风险范围”。

示例结构：

> 当前计划：8 个个人工作量点。过去 18 个“正常工作日”中，有 3 天的确认计划也在 7–9 点，其中 1 天完整兑现。样本很少，概率区间很宽，因此烛龙无法可靠判定；这不是过度承诺结论。若减少到 5 点，可比历史日增至 22 天，但仍需展示相应区间和结算分解。

禁止的表达包括：

- “你一天最多只能完成 3 项。”
- “难任务按 3 小时计算。”
- “AI 判断你明天一定做不完。”
- “延续三次说明你缺乏执行力。”
- “大多数用户每天做六项，所以你也应该如此。”

## 现有数据下可先落地的弱提示

在新增数据字段前，可做一个明确标注为“条数代理”的只读提示：

1. 只用锁定 Day Todo，分别展示近期和长期的每日最终任务总数、完成数及各种非完成结算数。
2. 把当前日期的任务条数放进同一用户历史分布中显示百分位。
3. 同时显示当前任务中有多少项没有子任务、工作量未知。
4. 若当前条数显著高于历史，文案只能说“任务条数高于你的历史常见范围”，不能说“已过度承诺”。
5. 延续次数只作为额外风险事实逐项展示，不能转换为统一的惩罚分。
6. 不满足相似日条件或历史太少时，明确显示“证据不足”。

这一路径有产品价值：它能把用户从模型感觉带回真实轨迹，同时不会虚构当前数据无法支持的容量精度。

## 不能由当前研究或数据推出的结论

- 没有证据证明个人 Todo 的最佳承诺阈值是固定的 70%、80% 或其他数值；它应由用户风险偏好和后续产品验证决定。
- 没有证据支持固定 7、14、30 或 90 天作为所有用户的最佳滚动窗口。
- 没有实际工时或专注记录，不能估算用户每天可用的真实小时数。
- 没有独立工作量字段，不能把任务条数、子任务数或 `简／中／难` 当作可比工时。
- 完成／未完成轨迹只能证明相关性，不能证明“安排过多”造成未完成。
- 延续、废弃或回池不提供心理归因，不能推断拖延、恐惧、动机或人格。
- 基于工程项目和实验室任务的 RCF／规划谬误证据支持方法方向，但没有直接验证上述具体算法在个人 Todo 产品中的效果。
- Wilson 区间不消除日与日之间的相关、季节性或生活阶段变化。
- NASA-TLX 说明工作负荷多维，不意味着 NASA-TLX 分数可以直接预测 Todo 完成量。

因此，正式发布“过度承诺风险”前需要前瞻性验证：预注册事件定义和参考类规则，在不改变用户计划的观察期内保存预测与结果，检查校准、误报、漏报，以及提醒是否真正改善“下一次可信承诺”，而不只是让计划数量变少。

## 建议的产品决策顺序

1. 先把能力命名为“承诺风险”，不用“能力评分”或“生产力分数”。
2. 明确定义承诺快照与兑现语义，尤其处理日内新增和 `changed`。
3. 新增独立的个人工作量单位；保留 `子任务难度权重` 原语义。
4. 设计可见、固定且可版本化的参考类选择规则。
5. 实现本地概率、Wilson 区间和“不确定／无资格判定”状态。
6. 保存预测与结果，建立校准报告。
7. 完成真实用户前瞻验证后，才决定默认风险阈值、窗口和强提醒门槛。

这能让烛龙做到“直指风险但不黑箱”：每次提醒都能回答用了哪些事实、比较了哪些历史、为什么得出这个范围、哪里还不知道，以及用户改动计划后风险如何变化。
