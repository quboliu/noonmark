# ADR 0040：把交互演示扩为一年可验证重放

- 状态：已接受
- 日期：2026-07-30

## 背景

ADR 0029 建立了由 `NoonmarkDemoSupport` 统一生成、经真实领域接口写入并从 SQLite 与加密 sidecar 回读的十天演示 fixture。它足以表达前景故事，却不足以暴露数据规模增长后才出现的输入延迟、投影扫描和持久化成本，也不能证明每项日常功能在长期使用中被重复行使。

腾讯拼音回显问题进一步证明，小数据量和仅验证最终值会漏掉真实交互退化：输入法 marked text 的每次变化曾触发共享状态发布、领域 snapshot 工作和持久化，并在主线程形成可感知阻塞。

## 决策

1. `NoonmarkDemoSupport` 的固定范围扩为截至锚点的 365 个连续自然日，仍只通过正式领域 mutation 建立事实。
2. 前 355 天构成长期历史负载，最后十天继续承载 ADR 0029 定义的可读前景故事。
3. 在四个季度分布十二个功能重放日；普通任务的二十九项创建、编辑、排期、排序、状态变更、复制、分类和子任务能力各至少真实使用十二次。
4. 每天至少有一条普通任务轨迹和一份日终复盘；年度日期必须无缺口、无重复，并跨冬夏令时边界。
5. 重复计划扩为十二条，四种父计划生命周期各三条，累计不少于五百个实例，并覆盖修订、跳过、改期、分类和规划子任务。
6. 烛龙会话扩为二十场。已提交任务、可编辑任务、习惯洞察、日终复盘和任务池分析五种会话在四个季度各出现一次。
7. `fixtureProfile` 固定为 `annual-v1`。覆盖报告、单元测试、真实 `.app` 探针、启动脚本和文档必须共同 fail-closed 检查年度规模。
8. 腾讯输入法性能矩阵默认安装这份年度负载，不允许用空库结果代替长期使用状态的结论。

## 后果

- 日常演示仍以最后十天为清晰的前景，不会因历史数据增长而失去可理解性。
- 输入、搜索、投影和存储实现必须在真实年度规模下维持交互预算。
- fixture 生成时间和真实 App 门禁时间上升；这是长期负载证据的必要成本。
- 新增普通用户能力时，若需要状态或历史才能体验，必须同时纳入年度功能重放计数和机器覆盖报告。
- 旧十天 fixture 不再是当前验收基线，也不得作为性能门禁的替代输入。

## 回滚

项目尚未发布并执行开发数据 clean cut。若年度 fixture 阻塞开发，只允许回滚本 ADR 及其实现提交后重新生成当前版本数据；不得保留、迁移或回读 `annual-v1` 数据。性能问题不得通过缩小 fixture、降低重复次数或放宽阈值规避。

## 验证

- `NoonmarkDemoSupportTests` 验证 365 个连续自然日、十二个跨季度重放日、二十九项能力各至少十二次及冬夏令时边界。
- `make test-demo-fixture` 通过真实 `NoonmarkDemo.app` 对账年度 SQLite、十二条重复计划、二十份加密 `.zhs` 会话和机器 manifest。
- `make test-tencent-ime-input-matrix` 在 `annual-v1` 上运行全部 53 个真实输入面。
- `make test-tencent-ime-termination-persistence` 在最终回显后立即退出并于重启后对账 SQLite 或加密 sidecar。
